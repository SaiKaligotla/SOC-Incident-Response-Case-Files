## Alert

The alert was triggered by rule **SOC113 – Suspicious hh.exe Usage** on host **BillPRD (`172.16.17.47`)** at **2021-01-31 16:59:42 (+03:00)**. The flagged process, `hh.exe`, opened a file named **`WinRAR.chm`** (306 KB, MD5 `07694464c25bac4ecdb365e928ffe1ff`). The device action is marked as **Allowed**, meaning the execution was not prevented.

`hh.exe` is the Windows HTML Help Viewer — the default handler for Compiled HTML Help (`.chm`) files. It is a legitimate signed binary, but adversaries abuse it to execute malicious scripts embedded in crafted `.chm` files (a living-off-the-land technique). Rule SOC113 therefore fires on hh.exe execution and requires the analyst to determine whether the opened file is malicious or benign.

At first glance the alert appeared suspicious: a file named after a popular archiver (WinRAR) launched via hh.exe, combined with proxy logs on the same host showing blocked requests to malware-serving URLs. Investigation was required to determine whether this was a true compromise or a false positive.

## Analysis

### Step 1 — Identify the file

The file opened by hh.exe is `WinRAR.chm`. WinRAR ships with an official, vendor-supplied help manual named exactly **`WinRAR.chm`** (typically located in `C:\Program Files\WinRAR\`). When a user opens WinRAR's Help (or presses F1), Windows launches `hh.exe` to display it. The flagged execution chain — `hh.exe` opening `WinRAR.chm` — is therefore expected, benign behavior that occurs on healthy endpoints.

### Step 2 — Third-party reputation check

The file hash `07694464c25bac4ecdb365e928ffe1ff` was checked via VirusTotal, ANY.RUN / Hybrid Analysis, and URLScan. Results:

- **No malicious detections** and no prior malicious submissions.
- Sandbox detonation showed the behavior of a clean help file: documentation renders, with **no script execution, no network connections, no dropped files, and no child processes**.

A clean hash combined with no malicious behavior and a filename matching known-good vendor documentation indicates a **non-malicious** file.

### Step 3 — Attribute the suspicious network traffic

The blocked requests to `115.99.150.132:56841/Mozi.m` (a Mozi botnet payload) and `jamesrlongacre.ac.ug/ac.exe` were examined for attribution:

- Both requests were generated by **`chrome.exe` (the web browser)**, parent `explorer.exe` — **not** by `hh.exe` and not by `WinRAR.chm`.
- A malicious CHM's network activity would appear under the **hh.exe** process. There was **no log of hh.exe initiating any network connection**, and hh.exe spawned **no child processes** (no `cmd.exe`, `powershell.exe`, `mshta.exe`, or `regsvr32.exe`).
- Both downloads were **Blocked** at the proxy — nothing was written to disk and nothing executed from those URLs. "Blocked" indicates a security control functioning at the network layer, not a compromised endpoint.

The blocked browser traffic represents unrelated web-browsing events on the same host, not C2 beaconing from the alerted file.

> **Distractor excluded:** a proxy record for `bit.ly/TAPSCAN` from host `10.15.15.12` on 2021-03-07 (resolving to `67.199.248.10`, Bitly infrastructure) was a different host, date, and link, and was ruled unrelated.

### Step 4 — Initial (incorrect) hypothesis and correction

During the first pass, the evidence appeared to form a complete attack chain: a lure file delivered via a shortened URL, executed by hh.exe, followed by requests to malware infrastructure. The alert was initially assessed as **Malicious / True Positive**, the host was contained, and C2 was marked "Accessed."

Re-investigation disproved this narrative on three points:

1. `WinRAR.chm` is the legitimate WinRAR help manual — not a lure.
2. The malware-related traffic belonged to `chrome.exe`, while `hh.exe` made no connections and spawned no processes.
3. The blocked downloads never reached disk; no endpoint compromise occurred.

## Containment

No containment action is required. The file opened by hh.exe is the legitimate WinRAR help manual, no malicious process activity or C2 contact is attributable to the alerted artifact, and the suspicious browser downloads were blocked at the proxy before reaching disk. The host **BillPRD (`172.16.17.47`)** is not infected.

The host containment performed during the initial (incorrect) assessment should be **reverted/lifted**, as it was not warranted.

No rule tuning is recommended: SOC113 behaved as designed by flagging hh.exe for human review, and the proxy blocks demonstrate the security controls functioning correctly.

## Lesson Learned

- **Dual-use tools are not inherently malicious.** `hh.exe`, `powershell.exe`, `mshta.exe`, and `regsvr32.exe` run on every Windows machine. The verdict depends on *what they open* — file path, process tree, and network behavior.
- **Pivot on the process, not just the host.** Logs sharing a hostname and timestamp are not automatically one incident. Malware traffic appears under the malware's process — here the suspicious requests belonged to `chrome.exe` while `hh.exe` was silent.
- **"Blocked" means the control worked.** A blocked download is a prevented attack at the network layer, not a confirmed infection.
- **A clean hash is evidence.** Zero detections plus benign sandbox behavior plus a filename matching legitimate software should shift the hypothesis toward non-malicious.
- **Know your software baseline.** Recognizing that WinRAR ships `WinRAR.chm` resolved the entire alert.
- **A rule firing correctly does not make a True Positive.** Behavioral rules are intentionally noisy on LOLBins; the analyst's job is the verdict. Challenging your own initial hypothesis is part of the process.

---

## Remediation Actions

- No remediation required on BillPRD — no malware present.
- Lift the host containment applied during the initial assessment.
- Continue user awareness coaching on avoiding suspicious downloads (the blocked `Mozi.m` / `ac.exe` requests indicate the user browsed to risky sites), though no infection resulted.
- Maintain existing proxy blocking and SOC113 monitoring; no detection tuning needed.
