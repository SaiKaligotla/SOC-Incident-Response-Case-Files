## 📋 Executive Summary

An alert fired for `hh.exe` opening a file named `WinRAR.chm` on host **BillPRD (172.16.17.47)**. Proxy logs from the same host showed blocked requests to URLs serving malware (including a **Mozi botnet** payload), which initially suggested a malicious CHM lure executing and beaconing to C2.

**Re-investigation proved the activity benign.** `WinRAR.chm` is the legitimate, vendor-supplied WinRAR help manual, which is opened by `hh.exe` — the standard Windows HTML Help Viewer. The blocked malware requests were generated by **`chrome.exe` (the browser)**, not by hh.exe, and both downloads were stopped at the proxy — nothing reached disk. A clean file hash, no child processes, and no network activity from hh.exe confirmed the verdict.

> **Core lesson:** pivot on the **process**, not just the host. Events sharing a hostname and timestamp are not automatically the same incident — correlation is not causation.

---

## 1. 🔎 Alert Context

`hh.exe` is the Windows **HTML Help Viewer** — the default handler for Compiled HTML Help (`.chm`) files. It is a signed, legitimate Windows binary, but attackers abuse it to execute malicious scripts embedded in crafted `.chm` files (**MITRE T1218.001**), typically delivered as lures and opened by the user (**T1204**).

Behavioral rules like **SOC113** therefore fire on *any* hh.exe execution and rely on the analyst to determine whether the file opened is malicious.

## 3. ❌ Initial Assessment (Incorrect)

During the first pass, the evidence appeared to form a complete attack chain:

1. User downloads a fake "WinRAR" file delivered via `bit.ly/3hNuByx` (proxy: **Allowed**).
2. User opens `WinRAR.chm` → `hh.exe` executes it → rule SOC113 fires.
3. The CHM's embedded script beacons out and attempts to fetch second-stage payloads (`Mozi.m`, `ac.exe`).
4. Conclusion: **Malicious / True Positive** — host contained, C2 marked "Accessed."

> **Result: 5/10 — the correct answer was Non-Malicious / False Positive.**

---

## 4. 🔄 Re-Investigation — What Was Missed

Four facts broke the attack narrative:

### 4.1 `WinRAR.chm` is a legitimate WinRAR file
WinRAR installs an official help manual named exactly **`WinRAR.chm`** (typically under `C:\Program Files\WinRAR\`). Opening WinRAR's Help (or pressing F1) launches `hh.exe` to display it. The "suspicious" execution chain was **expected, benign behavior on millions of healthy endpoints**.

### 4.2 The malware traffic belonged to the browser — not to hh.exe
The blocked requests to `Mozi.m` and `ac.exe` were logged under **`chrome.exe` (parent: `explorer.exe`)** — web-browsing activity. A malicious CHM's traffic would appear under **`hh.exe`**. There was **no log of hh.exe making any network connection**, and hh.exe spawned **no child processes** (no `cmd.exe`, `powershell.exe`, `mshta.exe`, `regsvr32.exe`).

### 4.3 The blocked downloads never landed
"Blocked" at the proxy means the connection/response was stopped at the **network layer** — no file was written to disk and nothing executed from those URLs. This is a security control working as designed, **not** evidence of a compromised endpoint.

### 4.4 The clean hash was evidence — not a tool failure
Zero detections, benign sandbox behavior, and a filename matching known-good vendor documentation all point to a **benign file**. The absence of threat-intel results was misread during the first pass.

> **Distractor excluded:** a log for `bit.ly/TAPSCAN` from host `10.15.15.12` on 2021-03-07 (resolving to `67.199.248.10`, Bitly infrastructure) was a different host, date, and link — unrelated to this alert.

## 8. 💡 Lessons Learned

1. **Dual-use tools are not inherently malicious.** `hh.exe`, `powershell.exe`, `mshta.exe`, and `regsvr32.exe` run on every Windows machine. The verdict depends on *what they open/run* — file path, process tree, and network behavior.
2. **Pivot on the process, not just the host.** Logs sharing a hostname and timestamp are not automatically one incident. The malware's traffic appears under the malware's process — here the suspicious traffic belonged to `chrome.exe` while `hh.exe` was silent.
3. **"Blocked" means the control worked.** A blocked download is a prevented attack at the network layer — not a confirmed infection.
4. **A clean hash is evidence.** Zero detections + benign sandbox behavior + a filename matching legitimate software should shift the hypothesis toward non-malicious.
5. **Know your software baseline.** Recognizing that WinRAR ships `WinRAR.chm` resolved the entire alert.
6. **A rule firing correctly ≠ a True Positive.** Behavioral rules are intentionally noisy on LOLBins; the analyst's job is the verdict. The detection worked as designed — the activity it caught was benign.
